# CLAUDE.md

Guidance for Claude Code (claude.ai/code) when working on this repository.

## What this repo is

`pob-mcp-server` — a TypeScript/Node MCP server that exposes the [Path of Building Community](https://pathofbuilding.community/) calculation engine to LLM clients. The server spawns a LuaJIT subprocess that runs PoB's real engine in headless mode and drives it via JSON over stdio.

PoB itself is an **external runtime dependency**. The user's PoB install at `%APPDATA%\Path of Building Community\` (or platform equivalent) provides `Launch.lua`, the calculation modules, and the lua libraries. The compiled Windows installer flattens those into the install root (`Launch.lua`, `Modules/`, `Data/`, `lua/`); a source clone keeps them under `src/` and `runtime/lua/`. `bridge.lua` detects which layout it's looking at via `arg[1]` and sets `package.path` accordingly. This repo owns only the Node server, the Lua bridge adapter, and tests.

## Common commands

```bash
npm install
npm run build         # tsc to dist/ (fails on tsc errors), marks dist/server.js executable
npm run typecheck     # tsc --noEmit
npm run dev           # tsx src/server.ts (no build needed)
npm run start         # node dist/server.js (built artifacts)

# Tests — POB_PATH must point at a real PoB install, or each integration test prints SKIPPED and exits 0
# (with REQUIRE_POB=1 it fails instead; CI sets it).
npm run test:paths    # unit tests for paths / discovery / config store (no LuaJIT needed)
npm run test:startup  # builds, starts dist/server.js unconfigured, configure_pob_path, saved config, reload_engine, elicitation
npm run test:safety   # engine safety tests
npm run test:bridge   # ~10s, Lua bridge round-trip — run first when debugging
npm run test:session
npm run test:server
npm run test:phase3   # item swap / compare
npm run test:phase4   # passive tree
npm run test:phase5   # gems
npm run test:build-edit  # apply_changes, create/delete_socket_group, set_main_skill: parity, refusals, undo, crash replay, fault seams
npm run test:phase6   # config / scenarios
npm run test:phase7   # diagnostics / upgrades / export / snapshots
npm run test:integrity  # bit-exact snapshot/restore stress
npm run test:crash-recovery  # crash breaker, timeouts, respawn restores the last committed build
npm run test:trade    # generate_trade_search / search_trade_mods (PoB's weighted trade query generator)
npm run test:probe    # read-only probe engine: parity with mutate+recalc, fallbacks, speed, the what-if tools on it
npm run test:evaluate # evaluate_changes: mixed 30-variant ranking, parity with single probes/tools, mastery / mainSkill rows, build unchanged
npm run test:stat-weights  # stat_weights (custom-modifier lines on the probe, parity with config customMods, unparsed lines) + suggest_upgrades' PoB-weighted mods
npm run test:compare  # compare_builds: diff vs a changed export (live numbers), live build untouched, temporary engine killed, crash/timeout/startup faults, concurrency
npm run test:lua-compat  # lua/compound-assign.lua rewrite of PoB 2.68's `x += 1` syntax (LuaJIT only, no PoB)
npm run test:wickerman  # 3.30 Wickerman slots: tree-gated slot listing/refusal, Viscera game text
npm run test:errors   # input validation paths
npm run test:all      # everything, in parallel (~2.5 min on a desktop); `npm run test:all -- bridge phase4` runs a subset
```

Single test: `tsx test/<file>.ts` — they're plain Node scripts.

`test:all` is `scripts/run-tests.mjs`: it runs every `test:*` script of `package.json` (a new one is picked up automatically; its command must be `tsx test/<file>.ts`), several at a time, each in its own process, and prints each script's output when it ends. `--jobs N` or `TEST_JOBS=N` sets how many run at once (default: CPU count, at most 6). A test script must therefore not depend on what other scripts are doing on the machine; one that has to (`test:startup` counts every LuaJIT process) is listed in `EXCLUSIVE` in the runner and runs alone at the end. While implementing, run only the scripts that cover the change; run `test:all` once before a push or PR.

Path resolution order: **env var → saved config (`configure_pob_path`) → auto-detect probe table** (`src/paths.ts`, `src/luajit-paths.ts`). Errors list everything probed.

Env vars:
- `POB_PATH` — PoB install (PoE1 only; the PoE2 edition is rejected). If set but invalid, auto-detect is skipped. Auto-detect probes `%APPDATA%\Path of Building Community`, the installer's `HKCU`/`HKLM` uninstall key `...\Uninstall\Path of Building Community` → `InstallLocation`, `%ProgramData%\Path of Building`, `%LOCALAPPDATA%\Programs\Path of Building Community`; macOS `~/Library/Application Support/Path of Building Community`; Linux `~/.local/share/...`, Flatpak, `/opt/path-of-building`.
- `LUAJIT_PATH` — `luajit` binary or a folder containing it. The Windows PoB installer does **not** ship `luajit.exe` (only `lua51.dll`); probes `<POB_PATH>/runtime/`, `%LOCALAPPDATA%\Programs\LuaJIT\bin`, scoop, Homebrew, `/usr/{local/,}bin`, then PATH.
- `POB_MCP_CONFIG_DIR` — overrides the saved-config dir (default `%APPDATA%\pob-mcp-server`, `~/Library/Application Support/pob-mcp-server`, `$XDG_CONFIG_HOME|~/.config/pob-mcp-server`). Tests must always set it to a temp dir.
- `POB_TIMING=1` — per-command timing on stderr.
- `REQUIRE_POB=1` — tests only: a missing PoB, LuaJIT or `POB_SOURCE_PATH` fails the test instead of printing `SKIPPED` and exiting 0 (`skipOrFail` in `test/_skip.ts`). CI (`.github/workflows/ci.yml`) sets it and points `POB_SOURCE_PATH` at a clone of the pinned `POB_TAG` and `POB_PATH` at a copy flattened into the installed layout.

## Architecture

```
Claude Desktop  <-stdio MCP->  pob-mcp-server  <-stdio JSON->  bridge.lua (LuaJIT)
                                                                       |
                                                                       v
                                                       <POB_PATH>/src, runtime/lua/, ...
```

| Layer | File | Job |
|---|---|---|
| Path resolution | `src/paths.ts`, `src/luajit-paths.ts`, `src/path-utils.ts` | `resolvePoB()` / `resolveLuaJIT()` / `resolveAllPaths()` — env var, saved config, probe table, error listing probes. Single source of truth for install discovery. |
| Install inspection | `src/pob-install.ts` | Layout + `manifest.xml` version, PoE2 detection, install fingerprint (version + mtime), PoB self-updater state (`Update/opFile.txt` = staged, `Update/manifest.xml` without it = applying). Read-only. |
| Config store | `src/config-store.ts` | Per-user `config.json` written by `configure_pob_path`. |
| Engine manager | `src/engine-manager.ts` | Owns the LuaBridge + BuildSession pair. Lazy/background boot, `run()` gate (unconfigured / updating / stale → `EngineNotReadyError`), `configure()`, `reload()` (export build → dispose old bridge → boot → reload build), `info()`. |
| Lua bridge | `lua/bridge.lua` | Stubs out PoB's graphics host (the same job upstream's `HeadlessWrapper.lua` does for the busted test suite), loads PoB's files through `lua/compound-assign.lua` (rewrites `+=`-style syntax plain LuaJIT can't parse), runs `Launch.lua`, reads JSON commands from stdin, dispatches to `build.itemsTab`, `build.skillsTab`, `build.spec`, `build.configTab`. PoB classes are created through `construct(className, ...)`, which detects once whether PoB uses 2.68's `new("X"):X(...)` or the older `new("X", ...)`. Knows nothing about MCP. |
| BuildSession | `src/build-session.ts` | TS class owning the LuaJIT subprocess. Snapshot/restore, undo stack, `withTemporaryChange`, async mutex, build-code/URL/XML loading, higher-level workflows. |
| Probe engine | `lua/probe.lua`, `src/probe.ts` | Read-only what-ifs: `BuildSession.probe(req)` evaluates variants (`allocate` / `deallocate` node ids, `masteries` [{node, effect}], `items`, `gems` ops, `config`, `mainSkill` {group, activeSkill?}) through PoB's calculator (`CalcsTab:GetMiscCalculator`, what its tooltips use), ~3-5 ms each, without changing or recalculating the committed build. Kinds it cannot reproduce exactly come back `fallback` and run through the snapshot/apply/recalc/exact-restore path (at most `MAX_FALLBACK_VARIANTS` = 50 per call; `MAX_PROBE_VARIANTS` = 500 variants per call); per-variant `error` / `userError`. |
| Searches on the probe | `src/tree-search.ts`, `src/link-search.ts`, `src/evaluate-changes.ts`, `src/stat-weights.ts` | `find_best_next_nodes` / `find_worst_allocated_nodes`; `find_optimal_links`; `evaluate_changes` (many mixed variants, node names resolved by `BuildSession.probeNamed`, a compact table ranked by one stat); `stat_weights` (`BuildSession.probeModLines`: PoB's mod parser checks each line (`probe` with `parseModLines`), then one `modLines` calculator variant per usable line: its mods appended to a copy of the config mod list, as the Custom modifiers box adds them; never in a fallback or `apply_changes`). `suggest_upgrades` takes its suggested mods from PoB's `TradeQueryGenerator` (the bridge's `tradeQuery`, `topTradeMods`) for the highest-priority slots only. |
| Build comparison | `src/compare-builds.ts` | `compare_builds`: side A is the loaded build, read with the bridge's read-only `compareSnapshot` under the session lock (or the `against` build); side B is loaded into a temporary engine (`EngineManager.withTemporaryEngine`) and read with the same command. The diff (stats, tree, items by slot, socket groups, meta, config) is computed in TS, lists capped with `more` counts. |
| MCP server | `src/server.ts`, `src/tool-registry.ts`, `src/engine-tools.ts`, `src/build-edit-tools.ts`, `src/compare-builds.ts` | Registers 48 tools via `@modelcontextprotocol/sdk`, validates with Zod + `UserError`, formats responses as compact JSON (`textResponse`; no pretty-printing). Every tool's MCP annotations (`readOnlyHint` / `destructiveHint` / `idempotentHint` / `openWorldHint`) live in `TOOL_ANNOTATIONS` in `src/tool-registry.ts`, keyed by name; a new tool needs an entry (`test:server` checks). `tools.engine(...)` handlers run inside `engine.run()` (shared gate slot + readiness checks) and receive the live session; `tools.plain(...)` handlers (configure_pob_path, get_engine_info, reload_engine, list_scenarios) work without an engine. |

## Non-negotiable invariants

- **The server never exits because PoB/LuaJIT is missing.** The MCP transport connects first; paths resolve and the engine boots in the background. While unconfigured, engine tools return `isError` text naming `configure_pob_path` (and elicit the path once when the client supports form elicitation). Nothing but MCP frames on stdout — log to stderr.
- **One persistent engine per session; `compare_builds` may start one short-lived read-only engine per call, killed when the call ends.** The temporary engine (`EngineManager.withTemporaryEngine`) runs on the live engine's paths, one at a time (a mutex), inside the calling tool's shared gate slot (swaps wait for it; `shutdown` / `killProcess` kill it too). It is never respawned (`setRespawnHeld` right after start), is always disposed in `finally`, and its strikes are its own: it never takes part in the `CrashLedger`, so its crash, timeout or failed start fails only that call (`TemporaryEngineError`) and never counts against the live engine's breaker. Right before spawning it gets the same install checks as engine tools (PoB applying an update, or changed on disk since the live engine started → `EngineNotReadyError` naming `reload_engine`), and it is refused (a `UserError`, no process started) while the live engine's crash breaker is open for these paths. Its error text never carries the live engine's crash wording (strike counts, "the next tool call restarts the engine"). It does not hold the session lock, so other engine tools keep running while it works. Engine boot is ~2s; pre-warmed in the background after connect. Engine-backed tool calls hold a shared slot in `EngineGate` (`src/engine-gate.ts`); an engine swap (`reload_engine` / `configure_pob_path`) takes it exclusively, waits for running calls, then disposes the old bridge before booting the new one. `LuaBridge.dispose()` always kills the captured process and rejects any pending call with a retry `UserError`; a disposed bridge refuses to respawn.
- **Never auto-restart on a PoB update.** The manifest version + mtime are recorded at engine start; if they change, engine tools error and point at `reload_engine`. Never write to the PoB directory.
- **Serial execution via async mutex.** PoB is single-threaded with shared globals. Two ops at once corrupts state.
- **What-ifs run through the probe engine.** Every `simulate_*`, `compare_*`, `find_*`, `evaluate_*`, `swap_gem`, `toggle_buffs`, `stat_weights` and `suggest_upgrades` evaluates its variants through PoB's calculator via `lua/probe.lua` (`BuildSession.probe`), which never changes or recalculates the committed build and must give the same numbers as mutate + full recalc (`probe-test.ts`). Config changes (calculator and fallback variants) run on copies of the active config set's `input` / `placeholder` tables; the original tables are put back unwritten (PoB 2.67 exports them in `pairs()` order), and the probe fingerprint includes both tables in `pairs()` order. One mastery change (allocating a mastery with an effect, or a new effect on an allocated one) goes through the calculator with a copy of the mastery node carrying that effect's stats in `addNodes` (with its path, or in place of the allocated node, which goes in `removeNodes`), as PoB's power builder evaluates mastery effects; the committed node is never changed. `mainSkill` sets `build.mainSocketGroup` and the group's `mainActiveSkill` for the calculator and puts them back. Kinds the calculator can't reproduce exactly (several node or mastery changes in one variant, a mastery in a timeless jewel's radius, jewel sockets, skill-granting nodes or items) come back `fallback` and use the snapshot / apply / full recalc / exact restore path in `try/finally`, under the restore exactness rules below; around every fallback variant the committed state is fingerprinted by value (`probe` with `fingerprint`), and a restore that leaves it different is an internal error naming `reset_build`. `simulate_passive_change` requests other than one allocation on a connected tree still apply, recalc and restore the passive tree (`withTreeProbeUnlocked`). Fallback restores must be bit-exact (`Life`, `CombinedDPS`, `TotalEHP` spot-checked in `state-integrity-test.ts`). Items are restored by id (`captureItemsState` / `restoreItemsState` in `lua/bridge.lua`): every non-socket slot the engine has re-selects its item and items added since the snapshot are deleted, so the item list and export stay unchanged (`item-restore-test.ts`). Passive-tree jewel sockets belong to the tree state (`spec.jewels`), never to the item state. Items present when any live snapshot or undo entry was taken are never deleted, so the ids they hold stay valid. Skills are snapshotted as every plain field of every socket group and gem in every skill set, plus set order, the active set, the skills tab settings and the main socket group (`snapshotSkills` / `restoreSkills`); the export stays byte-identical (`skills-restore-test.ts`). What-if probes restore through `probeThenRestore`: if the restore fails the result is an internal error that keeps the probe's error as `cause` (undo and `reset_build` do not use it). A skills restore that cannot relink a monster-explosion gem to its source raises an internal error instead of differing silently. Batch commands (`replaceSocketGroup`, `allocNodes`, `deallocNodes`) check the whole batch before changing anything, so a user error leaves the build untouched.
- **Masteries are chosen with an effect, never allocated bare.** A mastery in `allocate` / `nodes` is a `UserError` pointing at `masteries` [{node, effect}] (`nodeBatch.resolveMasteries` in `lua/bridge.lua`: node by id or name, effect by id or text; a name picks the allocated mastery of that name that has the effect already, else the only allocated one (a switch), else the only reachable one, and refuses anything else with the ids; refused before any change: not a mastery, an effect the node does not offer, an effect chosen on another mastery (PoB's mastery popup offers each effect once), a tattooed/runegrafted mastery, no path, listed twice, and a mastery the same variant's deallocations remove (the calculator would drop it, a fallback / `apply_changes` would re-allocate it with a path)). A request of only masteries that already have their effect is `unchanged`: no change, no undo entry, no journal record (`allocate_nodes`, `apply_changes`). A calculator-path effect switch checks the replaced node as a deallocation (`nodeFallbackReason`) and the new effect for a granted skill. `mainSkill` with an item or node change that may add or remove granted skill groups is a `UserError` (the group index could shift). `allocNodesBatch` sets each selection right before its mastery is allocated (PoB's `BuildAllDependsAndPaths` drops a selection on an unallocated mastery and gives an allocated one its effect's stats) and, for an allocated mastery switching effect, sets it and rebuilds; unallocated masteries go after the batch's nodes. There is no bare "clear effect": deallocating the mastery clears it. Tree state (`masteryEffects`) and the probe fingerprint already cover selections, so undo and restores stay exact.
- **Three-strike crash circuit breaker.** After 3 strikes the server refuses respawns (a `UserError` with the `circuitOpen` text; no process is started). Don't disable — it prevents silent respawn loops. A strike is any LuaJIT exit not asked for with a `shutdown` command, a command timeout (the process is killed), or a startup that fails or times out after the process ran (it is killed; nothing is left running unready). Strikes are never forgiven by later successful commands. The count is kept per (pobPath, luajitPath) in `CrashLedger` (`src/crash-ledger.ts`) and handed to each new bridge, so engine swaps can't reset it; it clears only when that PoB install changes on disk relative to the fingerprint taken when the crashing engine was started, or when the server process restarts. Keys use the real path of both files (lower-cased on Windows), so spelling variants share one count.
- **Crash recovery restores the last committed build, and says so once.** The bridge keeps a recovery build: the XML of the last `loadXML` the engine *accepted* (a rejected build is never recorded) plus a journal of the commands committed since (`swap_item` / `unequip_item` / `set_config` / `allocate_nodes` / `deallocate_nodes` / `convert_tree_to_latest` / `apply_changes` / `create_socket_group` / `delete_socket_group` / `set_main_skill` record their bridge command (`allocate_nodes` records the added node ids in the order they joined the tree, so a replay does not depend on which of several equally short paths PoB picks; `allocate_nodes` with `masteries` also records them as node id + effect id; `apply_changes` records its variant with gem names as PoB names them, the allocated node ids in that join order (masteries among them) and its masteries as node id + effect id; build edits are recorded with `replay: true`, which the bridge's test faults skip), together with their undo entry, only once the whole tool call succeeded, or when the call failed after the engine applied the change while the engine is still alive (then the internal error says the change was applied and undo_last_change reverts it); with the engine gone nothing is recorded; undo entries remember the journal length and `undo_last_change` truncates back to it). The journal is not bounded: there is no exact, side-effect-free point to fold it into a new baseline. It is not refreshed with `exportXML`: PoB's save re-parses every item of the live build. A dead engine is respawned only at the start of a locked `BuildSession` operation, and the respawned process reloads the XML and replays the journal. While an operation runs the bridge refuses to respawn (`setRespawnHeld`), so a crash or timeout part-way through fails that call (no rollback or probe restore runs against a fresh engine). The first call after a respawn throws `EngineRestartedError` (a `UserError`) naming the strike count, the restored build, and how many undo entries were cleared — undo entries hold per-process item tokens, so they are dropped; labelled stat snapshots (stats only) are kept; `reset_build` still returns to the originally loaded build. That call does nothing else. `load_build` / `reset_build` skip the notice and the replay (they replace the build): a respawn for them starts blank, a successful load carries the strike once in an `engineRestart` note, and a rejected load puts the last committed build back (then the next call gives the notice). A restore that fails marks the recovery build lost: it is kept for engine swaps, never replayed again, and every later restart reports it as failed. An engine swap whose engine already crashed carries the accepted XML, or restarts the old engine once to export the replayed build; when that is impossible (breaker open, the restart or its replay failed, or the build was lost) it carries the last accepted XML with a `buildNote` saying which committed changes are missing.
- **Test fault seam.** `POB_MCP_TEST_FAULTS` (read by `lua/bridge.lua`) reaches the LuaJIT child only through the `LuaBridge` `testFaults` option; the server's own environment value is stripped. Faults may only raise an error, exit the process or stall, or, for rollback-check faults (`treeRollbackInexact`, `buildEditRollbackInexact`), make the rollback or its fingerprint read come back different — never write files or print to stdout. `buildEditRollbackInexact` only marks the fingerprint read sent with `rollbackCheck`; any other fingerprint read disarms it.
- **Tool arguments are untrusted.** `configure_pob_path` arguments are never env-expanded (no `%VAR%`/`$VAR` leaks via error text), and a `luajitPath` argument must be an existing file named `luajit*` (`.exe` on Windows, no scripts) because it is executed. Network/device paths (`\\host\share`, `//host/share`, `\\?\…`, `\\.\…`) are refused for tool/elicitation arguments by a string check before any filesystem access. A saved-config `luajitPath` is re-checked with the same rules at startup and ignored (stderr warning) if it fails.
- **Mutations push to the undo stack.** `swap_item` and `unequip_item` (full snapshot; nothing is pushed when the bridge refuses the change with a user error, e.g. an item that does not fit the slot), `set_config` (config entry), `allocate_nodes` / `deallocate_nodes` (a tree entry: the whole spec state, mastery selections included, restored exactly by `restoreTreeUnlocked`; nothing is pushed when the bridge refuses the batch; `allocate_nodes` `masteries` allocates masteries or switches an allocated one's effect), `apply_changes` (one full snapshot for the whole variant; the bridge checks the variant first, gem changes by applying them to copies and undoing them, config keys that change a value are set on copies of the config tables, which stay live, and the committed tables are remembered unwritten under the snapshot's `ConfigSnapshot.token` (`ConfigTables.remembered` in `lua/bridge.lua`, also used by full-snapshot probe fallbacks; at most 64, emptied by every `loadXML`): only the restore sent with that token (the rollback or undo of that change, the fallback's own restore) puts those very tables back, so they keep their `pairs()` order, and no other restore ever attaches them; options that already hold their value make no copies, and a variant that fails part-way is rolled back to that snapshot and checked by value against the probe `fingerprint` taken before the command: an exact rollback pushes nothing; a rollback that fails or differs is an internal error naming `reset_build` that pushes the undo entry (undo can restore the pre-call build, as for the tree edits) and journals nothing), `create_socket_group` / `delete_socket_group` / `set_main_skill` (a skills entry restored by `restoreSkills`) and `convert_tree_to_latest` (a spec-level entry that carries the old tree version; nothing is pushed when already on the latest tree) push; no other tool does. Build edits other than node batches record how far they got in the bridge's `buildEdit.record` (read with `buildEditApplied` after a failure): not started → nothing to do, started → roll back, applied → commit with the applied-but-failed error. What-if tools (`evaluate_changes`, `simulate_passive_change`, `swap_gem`, ...) run on the probe engine, never change the build and push nothing; `apply_changes` commits one `evaluate_changes` variant with the same apply steps (`applyChanges` in `lua/probe.lua`). `undo_last_change` pops; `reset_build` reverts to the originally-loaded XML.
- **Error classification.** User-input errors (bad slot, unknown gem) → `UserError`, surfaced verbatim. Anything else → "Internal error: ... try reset_build".

## Adding a tool

1. Extend `lua/bridge.lua` with a new dispatch case.
2. Expose it in `BuildSession` (route mutations through `withLock`, push to undo stack as needed).
3. Register a Zod-validated entry in `src/server.ts` with `tools.engine(name, schema, async (args, session) => ...)`.
4. Add its MCP annotations to `TOOL_ANNOTATIONS` in `src/tool-registry.ts` (`readOnlyHint: true` only if it never changes the build). Return plain objects: the registrar sends them as compact JSON.

All engine-backed tools follow this pattern.

## Conventions

- **Item text format** in MCP tools comes from PoB's "Copy item" (right-click) — must start with a `Rarity:` line. The server validates strictly. The one exception is Viscera (Wickerman) item text copied from the game: first line `Item Class: Viscera`, no `Rarity:` line (PoB parses it as Normal). A leading UTF-8 BOM is stripped before the text reaches the engine (`normalizeItemText`).
- **Slot visibility.** Slots PoB shows only on some passive tree versions (Wickerman `Head`/`Body`/`Arm`/`Leg` on 3.30, `Graft 1`/`Graft 2` on 3.27; PoB's own `slot.shown`) are left out of `list_valid_slots` while hidden, and `swap_item`, `compare_items` and probe item variants (`evaluate_changes`, `suggest_upgrades`, ...) into them are a `UserError` (naming the remedy) before any change. `unequip_item` on a hidden slot is allowed, and `list_equipped_items` lists an occupied hidden slot with `hidden: true` and a note: PoB still counts a hidden Wickerman item (CalcSetup's `^Wickerman ` check matches no slot name) but skips a hidden graft. Items already in a hidden slot are kept by export, probes and undo. Weapon swap, Ring 3 and abyssal sockets are listed and accepted regardless (`slotChecks` in `lua/bridge.lua`).
- **Build code round-trip is lossless.** `export_build({format:"code"})` produces a base64 zlib string that `load_build` accepts back. Same for `xml`.
