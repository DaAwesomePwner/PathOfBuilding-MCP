## Engine and PoB install

- The bridge never writes inside the PoB install: writes, removes and renames targeting it are refused, and only plain read modes (`r`, `rb`) are allowed there. Why: the old stubs could truncate PoB's cached jewel data and trigger its updater. (2026-11-12, launch-critical-fixes, ed9853dd)
- When PoB changes on disk under a running server, engine tools return an error naming `reload_engine`; the server never restarts the engine silently. Why: a silent restart would clear undo history unnoticed. (2026-11-12, launch-critical-fixes, a4b9218e)
- A failed `loadXML` keeps the previously loaded build active; the engine goes blank only when there was none or restoring it fails, and the error says which. Why: the TypeScript session still holds the previous build's state. (2026-11-12, launch-critical-fixes, ed9853dd)
- Config keys are validated against the running engine's own config metadata before any mutation; unknown keys are a `UserError`, and presets or aliases must fail loudly if PoB renames a key. Why: dead keys silently did nothing. (2026-11-12, launch-critical-fixes, bdbe9663)
- PoB 2.68+ runs under plain LuaJIT: the bridge's module loader rewrites compound assignments (`x += 1`, `s ..= t`) only in a file that fails to parse and keeps the original parse error when the rewrite does not help, and PoB objects are created through a `construct()` helper that detects 2.68's split constructors (`new("Item"):Item(raw)`) once. Why: PoB 2.68.1 ships a patched LuaJIT, and the server could not boot against it. (2026-11-21, speed-build-iteration, 63df0382)
- PoB 2.69 runs under plain LuaJIT too: the same loader, under the same rules, also rewrites the safe-navigation operator `?.` (`<recv>?.<chain>` → a local helper call with the chain in a closure: receiver evaluated once, the chain only when it is not nil, one value), and CI pins `v2.69.0`; the other LuaJIT 3.0 syntax that upstream LuaJIT v2.1 backported (a2ce8114: bit operators, `?:`, `??`, `continue`, `const`, ...) is not rewritten until a PoB release uses it, and `a:m?.(x)` or a `...` in a chain is left alone (the file keeps its parse error). Why: PoB's LuaJIT is upstream v2.1 with that backport, and 2.69.0's `Classes/CompareBuySimilar.lua` (`(name)?.:lower()`) stopped the server booting on older LuaJIT (Linux packages, the LuaJIT installs users have). (2026-11-27, pob-269-compat, this branch)
- `compare_builds` evaluates the other build in a temporary, short-lived, read-only second LuaJIT engine started for the call and always killed when it ends, never respawned; its strikes are its own (never in the `CrashLedger`), it gets the same install checks as engine tools right before spawning, and it is refused while the live engine's breaker is open. The invariant is "one persistent engine per session". Why: exact PoB numbers for both builds without touching the loaded build, its undo history or crash journal; chosen by the user over a static XML diff or swapping builds in the live engine. (2026-11-22, build-comparison-theorycrafting, 729e8221)

## Items and slots

- Slot lists and slot checks follow PoB's own visibility for tree-gated slots only (Wickerman `Head`/`Body`/`Arm`/`Leg` on 3.30 trees, `Graft 1`/`Graft 2` on 3.27 trees): `list_valid_slots` leaves a hidden one out and equipping into it is a `UserError` naming the remedy, but an item already there is listed by `list_equipped_items` (marked hidden) and can be unequipped. Weapon-swap slots, `Ring 3` and abyssal sockets keep listing and accepting items as before. Why: match PoB's UI; PoB 2.68.1 still counts Wickerman items in hidden slots (its calc check matches no slot name), so users must be able to find and remove them; hiding every slot PoB's UI hides would have refused weapon-swap and `Ring 3` swaps. Whether PoB counts an item in a hidden Wickerman slot is read once from PoB's CalcSetup source (`slotChecks.hiddenCounted`: counted while it has 2.68's `slotName:match("^Wickerman ")` check; PoB 2.69 checks the slot names and skips them), and `list_equipped_items`' note says which; a hidden graft is always skipped. (2026-11-27, pob-269-compat, this branch) Replaces: PoB 2.68.1 still counts Wickerman items in hidden slots, so the note always said PoB counts them (2026-11-17)
- Item text copied from the game for a Viscera item (first line `Item Class: Viscera`, no `Rarity:` line) is accepted, as PoB parses it as a Normal item; all other item text still needs a `Rarity:` line. Why: the game's copy of Wickerman parts has no rarity line. (2026-11-17, pob-330-compatibility, f91a6a6e)
- Item text for the AI comes from Path of Building's own data: `search_items`, `get_item_text`, `list_item_mods` and `build_item` are read-only and use PoB's unique/base data and spawn weights; `build_item` checks PoB's parse of the finished text against the request and refuses implicit lines PoB reads as headers or that change crafting rules, and rare names PoB treats as uniques; bench crafts are named by their mod text (PoB's bench list has no stable ids). Why: hand-written item text was the most error-prone step, and the checks keep a request from smuggling in mods or influences. (2026-11-22, build-comparison-theorycrafting, 801e07b6)
- Abyssal sockets are listed (with `parentSlot`) only while the parent's item has them, and passive-tree jewel sockets carry `allocated` (plus `requiresClusterIn` for a cluster socket not yet on the tree). A what-if that leaves a jewel in an unallocated tree socket (`compare_items`, probe and `apply_changes` item variants) is a `UserError` naming `allocate_nodes` unless the variant allocates it; `swap_item` still equips there with a note. Why: PoB ignores that jewel, so the what-if returned an empty diff that looked like "no change"; refuse rather than mislead. (2026-11-23, expand-item-type-trade-support, 6576dbb2)
- Flask slots expose PoB's per-slot active state: listings report `active`, `set_flask_active` commits it (one undo entry, crash journal, empty slot refused), probe and `apply_changes` variants take `flasks`, and an item what-if into a flask slot left inactive is a `UserError` (`compare_items` `activate: true` evaluates it switched on). The per-slot state is separate from the `flasks` config alias (`conditionUsingFlask`). Why: PoB counts a flask or tincture only while its slot is active, so every comparison in an inactive slot was zero. (2026-11-23, expand-item-type-trade-support, b58cab59)
- `suggest_upgrades` covers every item slot kind (gear of the weapon set in use, `Ring 3` while shown, flasks, allocated tree jewel sockets capped at 16 measured per call, abyssal sockets the parent's item has, tree-gated slots while shown), each row with `kind`. Empty gear and flask slots lead; inactive flasks, flasks adding nothing, unmeasured sockets and empty jewel, abyssal and Wickerman slots get `priority: null` and sort after the ranked slots, and the empty or unmeasured jewel / abyssal sockets and empty Wickerman slots among them never use the default `modSlots` budget (`slot` still reaches them); an engine error naming `reset_build` fails the call instead of becoming a `modsError`. Why: the gear-only list hid most upgrade options, empty sockets must not crowd gear out of the suggested mods, and a build left different must never pass as success. (2026-11-23, expand-item-type-trade-support, ecf47e28 / 9e6a7bcd)

## Snapshots, undo and recovery

- A what-if restore or an undo that cannot reproduce its snapshot exactly returns an internal error naming `reset_build`; it never leaves a silently different build. When a probe and its restore both fail, the result is internal and keeps the probe's message; a probe's user error stays a user error only if the restore succeeded. Why: a quietly wrong tree or item set gave wrong advice with no sign of it. (2026-11-13, backlog-restore-and-breaker, 83fb5934)
- Items are restored by item id, and items added since the snapshot are deleted; one that something still uses is kept and the restore fails with the internal error above; passive-tree jewel sockets belong to the tree state, every other slot to the item state. After a committed `swap_item` the replaced item stays in the build's item list until undo, reset or reload, as in PoB's own UI. Why: re-adding item text duplicated items and grew exports. (2026-11-13, backlog-restore-and-breaker, 8fbe9f26)
- An item that does not fit its slot, or item text PoB cannot parse, is a `UserError` raised before any change; batch commands (`replaceSocketGroup`, `allocNodes`, `deallocNodes`) check the whole batch first, so `simulate_passive_change` refuses unallocated or unreachable nodes instead of returning an empty diff. Why: PoB silently emptied the slot, and a bad element left a half-applied change. (2026-11-13, backlog-restore-and-breaker, 8fbe9f26 for items, 7d5ba562 for batch commands)
- `convert_tree_to_latest` keeps whatever the target tree supports, including a secondary ascendancy (bloodline) that PoB's own convert button drops, and replaces the active tree in place. Why: PoB's `CreateUndoState` loses the secondary ascendancy, and an extra tree would grow every export. (2026-11-13, backlog-restore-and-breaker, 7d5de800)
- After a crash the engine comes back with the last build it accepted plus a replay of the committed changes made since; a change is recorded for replay, and its undo entry pushed, only once the whole tool call has succeeded or the change is known to be applied on a live engine. Undo history is cleared by the restart and the user is told once: the first engine call fails with a restart notice, and `load_build` / `reset_build` succeed with a note instead. Why: the old respawn reloaded the originally loaded build and dropped committed changes without saying so. (2026-11-13, backlog-restore-and-breaker, c9b63635)
- What-if tools evaluate through PoB's own calculator (`calcsTab:GetMiscCalculator()`, driven by `lua/probe.lua`) and never change or recalculate the committed build; a probe that leaves the committed state different (fingerprint) is an internal error naming `reset_build`. Variant kinds the calculator cannot reproduce exactly (more than one node change, jewel sockets, skill-granting nodes or items) take the snapshot/apply/recalc/exact-restore path, at most 50 per call; at most 500 variants per call. Why: about 3-5 ms instead of about 270 ms per probe with bit-identical stats, approved by the user. (2026-11-21, speed-build-iteration, 8b09aaa0)
- Tree, gem, skill and build-level changes can be committed: `allocate_nodes` / `deallocate_nodes` (masteries via `masteries`), `apply_changes` (exactly one `evaluate_changes` variant as one undo step), `create_socket_group` / `delete_socket_group` / `set_main_skill`, `set_character_level` and `set_ascendancy`; each pushes one undo entry and one crash-journal record per successful call, nothing on a user error, and records already-resolved ids (node ids in the order they joined the tree, effect ids, gem names as PoB names them) so a replay never depends on names or Lua table order. Over-budget passive trees are allowed (negative `remaining`), as in PoB's UI. Why: the AI could simulate a theorycrafted build but never keep it, so `export_build` could not return it. (2026-11-22, build-comparison-theorycrafting, 22c7beb6 / 4fa82b83 / d4f168ca)
- `apply_changes` sets config keys on copies of the config tables and remembers the committed tables under its undo snapshot's token; only the restore carrying that token puts them back (never matched by value), so undo keeps PoB 2.67's `pairs()` export order. Why: writing into the live tables made rollbacks fail their exactness check about 3 runs in 4, and matching by value attached stale tables to unrelated restores. (2026-11-22, build-comparison-theorycrafting, 2d825b04)
- `new_build` goes through exactly the `load_build` path: its request (`<MCPNewBuild …/>`) is sent as the build XML and the bridge turns it into a blank build after validating class, ascendancy, bloodline, level and tree version, so undo reset, crash recovery, `reset_build` and the restart note behave the same; the level defaults to 1 in manual level mode (PoB's New uses auto); a class change in `set_ascendancy` is refused unless the tree connects to the new class start or `allowTreeReset` is passed. Why: auto level changes the level as passives are allocated and breaks parity between what-ifs and commits; a silent tree reset would lose the build. (2026-11-22, build-comparison-theorycrafting, d4f168ca)
- Test faults for rollback checks (`treeRollbackInexact`, `buildEditRollbackInexact`, `tradeFlaskRestoreInexact`, the last only for the fingerprint read after a trade search's flask activation is undone) may make the rollback or its fingerprint read come back different; every other fault may only raise an error, exit the process or stall. Why: a raised error never reaches the compare branch those faults exist to test. (2026-11-23, expand-item-type-trade-support, ecf47e28) Replaces: the same rule naming only `treeRollbackInexact` and `buildEditRollbackInexact` (2026-11-22)

## Configuration and security

- Path resolution order is environment variable, then saved config, then auto-detect; a missing PoB or LuaJIT never exits the server. Why: MCP clients only show "server disconnected" on exit, so the user could not be asked. (2026-11-12, launch-critical-fixes, a4b9218e)
- Paths supplied through `configure_pob_path` or elicitation are not environment-expanded and may not be network or device paths; `luajitPath` must be an existing file named `luajit*` (`.exe` on Windows). Paths from `POB_PATH`/`LUAJIT_PATH` keep expansion. Why: these values can come from the model, and they are executed or echoed back. (2026-11-12, launch-critical-fixes, a4b9218e)
- `load_build` URLs are accepted only for the exact hosts `pastebin.com` and `pobb.in` (with or without `www.`, as https or http links, default port only); the request is always made over https to a URL rebuilt from a fixed origin plus the build id, redirects are refused, and the fetch and the decoded build are size- and time-bounded. Why: the source string can come from the model, so the caller's URL must never reach `fetch`. (2026-11-13, backlog-ready-items, 65426efd)
- `load_build` downloads and decodes before taking the session lock, so overlapping loads take effect in completion order, not call order. Why: a slow fetch must not block every other engine call; making the later call win was not asked for. (2026-11-13, backlog-ready-items, 65426efd)
- The three-strike crash count is kept per resolved (PoB path, LuaJIT path) pair and clears only when that install changes on disk. Why: reconfiguring must not be a way around the breaker, and a PoB update must be a way out. (2026-11-12, launch-critical-fixes, a4b9218e)
- A crash-breaker strike is any LuaJIT exit that was not requested, any bridge command timeout (the process is killed) and any failed or hung startup; successful commands never forgive strikes. Why: strikes used to reset after five successful commands and timeouts never counted, so the breaker could not trip. (2026-11-13, backlog-restore-and-breaker, f1df96f9)
- `POB_MCP_TEST_FAULTS` (fault injection in `lua/bridge.lua`) is test-only: the server strips it from the LuaJIT child's environment and only a `LuaBridge` option or its test-only setter (`setTestFaults`) can set it; what a fault may do is under "Snapshots, undo and recovery". Why: tests need to fail the engine at exact points, and a stray client environment must not be able to turn faults on. (2026-11-13, backlog-restore-and-breaker, f1df96f9)

## Trade search

- Weighted trade searches (`generate_trade_search`) wrap PoB's own `TradeQueryGenerator` headlessly instead of reimplementing the weighting, and the result is an offline `https://www.pathofexile.com/trade/search/[<realm>/]<league>?q=<json>` link sorted by weighted sum; the server never contacts the trade site and never lets PoB download or save `QueryMods.lua`/`TradeSiteStats.lua` (a missing file is a `UserError`). Caller `weightAdjustments` on single resistance or attribute ids go to PoB's matching `pseudo.pseudo_total_*` filter and are never dropped by the 36-filter cap; `requiredMods` keep the exact id given. Why: the same weights as PoB's UI, no trade-API rate limits or login, no writes into the install, and no double-counted resistances; a pseudo total would loosen a required minimum. (2026-11-14, weighted-trade-search-generation, f9b595fc)
- A `weightAdjustments` weight on a stat PoB's trade generator deliberately leaves out (all elemental resistances, all attributes, hybrid resistance or attribute ids) is a `UserError` naming the `pseudo.pseudo_total_*` ids to adjust instead; weight 0 on such an id is a no-op, and the ids stay valid in `requiredMods`. Options given for a slot they do not apply to are accepted when they change nothing and refused when they would change the search. Why: those stats are already counted inside the pseudo totals, so a separate weight scores them twice; clients that always send default options must not fail. (2026-11-14, weighted-trade-search-generation, 356fe939)
- On PoB 2.68 the bridge turns the generator's query table back into the 2.67 JSON shape, lifts 2.68's complexity budget only while `FinishQuery` runs (a debug hook installed after the item calculation and removed as soon as it lifts) so the server's own 36-filter cap still decides, and adds the `pseudo.pseudo_has_*_influence` requirements 2.68 no longer adds (in the same "and" group as `requiredMods`, each id once; the weights are computed without influence on the test item, as 2.68 no longer models it); each step is chosen by what PoB provides, not by version. Why: keep generated searches the same on 2.67 and 2.68; 2.68's limit of 200 can still be exceeded, as with 2.67 (backlog). (2026-11-21, speed-build-iteration, fd37463d)
- Jewel slots are searchable: allocated passive-tree sockets with `jewelType` (`base` / `abyss` / `any`, passed as the generator's `options.jewelType`; default from the socketed jewel) and abyssal sockets the parent's item has; jewel slots refuse `sockets`, `links`, `influences` and `includeScourge: true`, and other slots refuse `jewelType`. Why: PoB's generator supports them but its popup was the only way in; options that cannot apply would silently change nothing or match nothing. (2026-11-23, expand-item-type-trade-support, 6576dbb2)
- Every flask kind is weighed from PoB's full `Flask` mod list and searched in the `flask` category; `flaskType` picks the flask the mods are tried on (the equipped one or a blank stand-in base), and an inactive flask slot is evaluated as active for the call, then restored exactly and checked by fingerprint (`evaluatedActive`). Why: PoB's `LifeFlask` / `ManaFlask` lists hold 7 mostly non-flask mods and PoB itself never uses them; an inactive slot gives every mod a zero weight. (2026-11-23, expand-item-type-trade-support, ecf47e28)
- A trade search into a weapon slot of the weapon set the build does not use, or an abyssal socket on one, is a `UserError`; `compare_items` there adds a note instead. Why: PoB skips those slots, so every weight would be 0. (2026-11-23, expand-item-type-trade-support, ecf47e28)
- `unique` runs PoB's special searches (Watcher's Eye in an allocated tree socket, Megalomaniac, Pearl of Tsoatha in a shown ring slot), each feature-detected; on top of PoB's own `containJewelSocket` check (never set in PoB 1) a socket holding a cluster jewel is refused, and Megalomaniac's default socket skips one. Unique searches always exclude mirrored items, and trade ids take up to two `|` suffixes so Pearl's filters can be adjusted or required. Why: replacing a cluster jewel drops its passives from every weight; matching PoB's popup otherwise. (2026-11-23, expand-item-type-trade-support, 412bea3b)
- Grafts and tinctures get weighted searches through PoB's own mod processing, filtered by base type because PoB's data has no trade category for them; graft implicits are not weighed, mod lines with no trade stat are reported as `unmatchedMods`, and an empty graft slot, a tincture search without a tincture in the slot, and `includeScourge: true` (plus `sockets`, `links` and `influences` on grafts) are refused. Wickerman slots return the fitting Viscera parts ranked by the stat weights (top 10) with no trade link, as PoB has no Viscera trade data. Cluster jewels have no weighted search (PoB has no category or mod list for them). Why: every item slot is either searchable with PoB's own numbers or refused with a specific reason. (2026-11-23, expand-item-type-trade-support, 9e6a7bcd)

## MCP tools

- `find_best_next_nodes` ranks every unallocated node within `maxPoints` of path cost (default 3) by gain per point by default; `find_worst_allocated_nodes` removes each node with its dependent subtree and ranks by loss per refunded point; slow candidates past the fallback cap are listed in `skipped`, never dropped silently. Why: adjacent-only, Normal-only searches missed notables a few points away and the real cost of removing a notable. (2026-11-21, speed-build-iteration, 1dfabe77)
- `find_optimal_links` takes its candidates from PoB's own support check (`calcLib.canGrantedEffectSupportActiveSkill`) and tests each support at its natural maximum level, capped at 20. Why: the tag match left out valid supports and suggested ones PoB says cannot apply, and a flat level 20 overrated Empower and Enlighten. (2026-11-21, speed-build-iteration, 2f5f22a4)
- `evaluate_changes` is the batch what-if tool: up to 500 mixed variants per call (nodes, masteries, items, gems, config, `mainSkill`), ranked by one stat or by a weighted `objective` (relative or absolute change; not together with `rankBy`), with optional hard `constraints` (variants that break one are listed after the passing ones, or dropped with `onlyPassing`), nothing applied. A node name used by more than one node it could apply to is a `UserError` listing the candidate ids (per variant in `evaluate_changes`). Why: the AI should try many combinations per round trip without a wrong node being picked silently. (2026-11-21, speed-build-iteration, b916bfea; objective and constraints 2026-11-22, build-comparison-theorycrafting, aefef670)
- Tool replies are compact JSON; `get_passive_tree`, `list_equipped_items` and `list_skill_groups` return compact defaults with a `detail`/`includeItemText` opt-in; `diagnose_build` and `suggest_upgrades` return one JSON part (`suggest_upgrades` no longer returns `currentItem`); tools that never change the build carry `readOnlyHint`, and `load_build`, `reset_build`, `configure_pob_path`, `reload_engine` and `undo_last_change` carry `destructiveHint`. Why: fewer tokens per result, and clients can auto-approve read-only tools. (2026-11-21, speed-build-iteration, b916bfea)
- `get_stats` category mode reads every key of the requested categories through the probe's base read, and `diagnose_build` reads the extra keys its checks need the same way; the default stat key list stays short. Why: categories and diagnostics referenced keys the bridge never returned, so crit, hit and suppression output was silently missing. (2026-11-22, build-comparison-theorycrafting, e5c37ec9)
- `stat_weights` measures each mod line as its own `modLines` probe variant (PoB's custom-modifier parse; unparsed lines are reported, never scored 0); `suggest_upgrades` takes each slot's suggested mods from PoB's `TradeQueryGenerator` weights for the highest-priority slots only (`modSlots`, default 3), the archetype regexes and mod table are gone, and an engine death mid-call fails the call. Why: build-specific numbers instead of hardcoded guesses, within a few seconds. (2026-11-22, build-comparison-theorycrafting, fb512fd0)
- Masteries: `get_passive_tree` `masteries` lists a mastery's effects; probe and `apply_changes` variants take `masteries` and `mainSkill`; a mastery that the same variant's deallocation removes, and `mainSkill` together with a change that may add or remove granted skill groups, are refused rather than evaluated differently by the calculator and the commit path. Why: `evaluate_changes` and `apply_changes` must give the same numbers. (2026-11-22, build-comparison-theorycrafting, ac192037)
- `plan_passive_points` / `plan_respec` are read-only planners: steps are allocated for real inside one tree + skills scope, candidates are probed from there, slow candidates are capped, a 40 s budget ends the search with the best applied plan, and one exact restore plus a by-value check closes the scope; results carry `apply_changes` / `allocate_nodes` arguments that reproduce the reported numbers. Why: multi-point planning on the fast calculator without committing anything. (2026-11-22, build-comparison-theorycrafting, 962b3ed8)

## Repository and CI

- The repository is public with its git history as it was; no history rewrite. Why: the user accepted the commit identities already in history, and GitHub keeps pull-request refs that a rewrite cannot clear. (2026-11-13, make-repo-public-add-ci, 4a5463fd)
- CI runs the full suite with `REQUIRE_POB=1` against a pinned Path of Building release and a pinned LuaJIT, on Ubuntu and Windows; the workflow uses `pull_request` (never `pull_request_target`), read-only permissions, no secrets, and actions pinned to commit SHAs. Why: fork pull requests run it, and a silent skip must not pass. (2026-11-13, make-repo-public-add-ci, 4a5463fd)
- CI tests only the pinned latest Path of Building release (now `v2.69.0`); support for older releases (2.67, 2.68) is best effort and checked by hand. Why: a second PoB job would double CI time for releases PoB updates away from on its own. (2026-11-17, pob-330-compatibility, 58a5b1a6)
- `npm run test:all` runs the test scripts in parallel through `scripts/run-tests.mjs`, each in its own process; a script that depends on machine-wide state (`test:startup` counts every LuaJIT process) is listed as exclusive and runs alone at the end. Why: run one after another the suite took over 10 minutes locally and 13 to 15 in CI. (2026-11-13, faster-tests-ci, f4f36678)
- While implementing, each phase gate runs the type check plus the test scripts that cover the change; the full suite runs once, before a push or pull request. Why: the user asked for fewer full runs to keep work quick. (2026-11-13, faster-tests-ci, f4f36678)
